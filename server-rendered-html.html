Django Components Testing Strategy

Architecture & Implementation Handoff Document

This document outlines the standard operating procedure for testing server-rendered Django components. Adhering to this strategy ensures our test suite remains incredibly fast, deterministic, and highly resilient against flakiness, while still thoroughly testing complex frontend interactions.

The Core Philosophy: Divide testing into two distinct layers. We unit test the markup and permutations using native Python tools (90% of tests), and we functionally test the client-side behavior using a real browser via Playwright (10% of tests).

1. The Two-Tier Architecture

Tier 1: Unit Rendering (90%)

Goal: Verify that given specific Python arguments (props), the component correctly renders the expected HTML strings, CSS classes, and attributes.

  • Tools: django.test.TestCase + BeautifulSoup4
  • Speed: ~5-15 milliseconds per test.
  • When to use: Testing size variants, colors, disabled states, conditional rendering, and slot injections.

Tier 2: Functional Interaction (10%)

Goal: Verify that JavaScript-driven state changes (HTMX, Alpine.js, Vanilla JS) function correctly when interacting with the DOM.

  • Tools: pytest + pytest-playwright
  • Speed: ~400-800 milliseconds per test.
  • When to use: Modal toggles, dropdowns, AJAX/HTMX form submissions, and complex DOM event listeners.

2. Implementation Guide: Tier 1 (Fast Unit Tests)

Do not use a browser for structural assertions. Instead, shallow-render the component using Django's template engine and parse the resulting HTML with BeautifulSoup. 

from django.test import TestCase
from bs4 import BeautifulSoup
from myapp.tests.utils import shallow_render_component

class ButtonComponentTest(TestCase):
    def test_button_danger_variant(self):
        # 1. Render in isolation
        html = shallow_render_component(
            "button",
            props={"variant": "danger", "disabled": True},
            slot_content="Delete"
        )

        # 2. Parse and assert intent
        soup = BeautifulSoup(html, 'html.parser')
        btn = soup.find('button')

        self.assertIn('bg-red-500', btn.get('class', []))
        self.assertTrue(btn.has_attr('disabled'))
        self.assertEqual(btn.text.strip(), "Delete")

3. Implementation Guide: Tier 2 (Playwright)

Reserve Playwright exclusively for components that contain client-side interactivity. To keep tests fast, do not load the full application layout; serve the component via a lightweight, isolated dummy route. 

import pytest
from playwright.sync_api import Page

@pytest.mark.django_db
def test_alpine_dropdown_opens_on_click(page: Page, live_server):
    # 1. Mount isolated component
    # /_test/components/dropdown serves only the component HTML
    page.goto(f"{live_server.url}/_test/components/dropdown")

    # 2. Locate elements
    menu = page.locator('.dropdown-menu')
    trigger = page.locator('text=Options')

    # 3. Assert JS Behavior
    assert not menu.is_visible()
    trigger.click()
    assert menu.is_visible()

4. Rules and Best Practices for the Team

  • Rule of Thumb: If you can test it by reading the HTML source code, write a Unit Test. If you have to physically click it to see the result, write a Playwright Test.
  • Parallel Execution: Always run Playwright tests using pytest-xdist (e.g., pytest -n auto). This dramatically reduces CI wall-clock time by utilizing all CPU cores.
  • Avoid Full Page Loads: When writing Playwright component tests, avoid routing through standard Views if possible. Inject the component into a blank template to bypass database queries, middleware, and heavy asset loads.
  • Form Submissions without JS: If a component is just a standard HTML form (no HTMX/AJAX), test the submission logic using django-webtest or the standard Django Test Client, not Playwright.
