Django Clean Architecture

A reference for building server-side HTML applications with clean architecture, the MVP presentation pattern, and django-components. Covers the full stack from domain entities to rendered HTML.

Django Clean Architecture django-components MVP Pattern HTMX

Server-Side HTML Philosophy

The core rule: the server owns all state and logic; the browser is just a renderer. The client sends HTTP requests, gets back HTML (full page or fragment), and displays it. No JSON APIs, no client-side state management.

Hypermedia as the Engine of Application State (HATEOAS) — the server encodes all current state in the HTML it returns, including the actions available. The client needs no prior knowledge of the application.
Browser                 Server
  │──── GET /cart ─────────► View
  │◄─── HTML (full page) ─── │
  │                            │
  │──── POST /cart/add ──────► Use Case
  │                            │  └─ mutates DB
  │◄─── Redirect 303 ─────── │
  │──── GET /cart ─────────► View
  │◄─── HTML (full page) ─── │

PRG Pattern

Post / Redirect / Get — you never render HTML directly after a POST. This prevents double-submit on browser back, keeps the URL meaningful, and separates mutation from display.

Form POST
→
Use Case (mutate)
→
Redirect 303
→
GET (render)

With HTMX, you swap fragments instead of full pages, but the server still produces HTML — not JSON. The architecture is identical; only the transport changes.

Domain Layer domain

Zero framework imports. Pure Python. This is where domain knowledge lives — business rules, invariants, domain language. The Cart entity knows the Quebec tax rate because that's a business fact, not a Django fact.

cart/domain/entities.pypython
from __future__ import annotations
from dataclasses import dataclass, field
from decimal import Decimal

@dataclass(frozen=True)
class Money:
    amount: Decimal
    currency: str = "CAD"

    def __add__(self, other: Money) -> Money:
        assert self.currency == other.currency
        return Money(self.amount + other.amount, self.currency)

    def __mul__(self, scalar: int | Decimal) -> Money:
        return Money(self.amount * Decimal(scalar), self.currency)

@dataclass
class Cart:
    session_key: str
    items: list[CartItem] = field(default_factory=list)

    TAX_RATE = Decimal("0.14975")  # Quebec HST+QST — domain knowledge

    def add(self, product_id: int, name: str, price: Money, quantity: int = 1):
        for item in self.items:
            if item.product_id == product_id:
                item.quantity += quantity
                return
        self.items.append(CartItem(product_id, name, price, quantity))

    @property
    def subtotal(self) -> Money:
        if not self.items:
            return Money(Decimal("0"))
        return sum((i.subtotal for i in self.items), Money(Decimal("0")))

    @property
    def tax(self) -> Money:
        return Money((self.subtotal.amount * self.TAX_RATE).quantize(Decimal("0.01")))

    @property
    def total(self) -> Money:
        return self.subtotal + self.tax

Application Layer application

Ports define what the use case needs as abstract interfaces. Use cases orchestrate domain logic. Neither imports Django, SQLAlchemy, or any framework.

Ports (Interfaces)

cart/application/ports.pypython
from abc import ABC, abstractmethod
from dataclasses import dataclass
from decimal import Decimal
from ..domain.entities import Cart

@dataclass
class ProductData:
    """What the use case needs — not the ORM model."""
    id: int
    name: str
    price: Decimal
    stock: int

class CartRepository(ABC):
    @abstractmethod
    def find_by_session(self, session_key: str) -> Cart | None: ...

    @abstractmethod
    def save(self, cart: Cart) -> None: ...

class ProductRepository(ABC):
    @abstractmethod
    def find_by_id(self, product_id: int) -> ProductData | None: ...

Use Cases

cart/application/use_cases.pypython
@dataclass
class CartOutput:
    """Output DTO — framework-free, handed to the presenter."""
    items: list[CartItemOutput]
    subtotal: Decimal
    tax: Decimal
    total: Decimal
    is_empty: bool

class AddToCartUseCase:
    def __init__(self, cart_repo: CartRepository, product_repo: ProductRepository):
        self.cart_repo = cart_repo
        self.product_repo = product_repo

    def execute(self, session_key: str, product_id: int, quantity: int = 1):
        product = self.product_repo.find_by_id(product_id)
        if product is None:
            raise ProductNotFound(f"Product {product_id} not found")
        if product.stock < quantity:
            raise InsufficientStock(f"Only {product.stock} in stock")

        cart = self.cart_repo.find_by_session(session_key) or Cart(session_key)
        cart.add(product.id, product.name, Money(product.price), quantity)
        self.cart_repo.save(cart)

class GetCartUseCase:
    def __init__(self, cart_repo: CartRepository):
        self.cart_repo = cart_repo

    def execute(self, session_key: str) -> CartOutput:
        cart = self.cart_repo.find_by_session(session_key) or Cart(session_key)
        return CartOutput(
            items=[CartItemOutput(...) for item in cart.items],
            subtotal=cart.subtotal.amount,
            tax=cart.tax.amount,
            total=cart.total.amount,
            is_empty=cart.is_empty,
        )

Infrastructure Layer infrastructure

Concrete implementations of the ports. This is where Django ORM lives. It maps between the ORM world and the domain entity world — the anti-corruption layer.

cart/infrastructure/repositories.pypython
class DjangoCartRepository(CartRepository):
    def find_by_session(self, session_key: str) -> Cart | None:
        try:
            record = CartRecord.objects.prefetch_related('items').get(
                session_key=session_key
            )
        except CartRecord.DoesNotExist:
            return None

        # ORM → domain entity mapping (anti-corruption layer)
        cart = Cart(session_key=session_key)
        for item_record in record.items.all():
            product = Product.objects.get(pk=item_record.product_id)
            cart.items.append(CartItem(
                product_id=item_record.product_id,
                name=product.name,
                unit_price=Money(product.price),
                quantity=item_record.quantity,
            ))
        return cart

    def save(self, cart: Cart) -> None:
        record, _ = CartRecord.objects.get_or_create(session_key=cart.session_key)
        record.items.all().delete()
        CartItemRecord.objects.bulk_create([
            CartItemRecord(cart=record, product_id=item.product_id, quantity=item.quantity)
            for item in cart.items
        ])

Interface Adapters interface

Views, presenters, and components. This is the translation zone between the application and the outside world. Views wire everything together and make no decisions.

The view's four-step job: (1) parse the request, (2) call the use case, (3) call the presenter, (4) render what comes back. Nothing else.
cart/interfaces/views.pypython
class CartView(View):
    def get(self, request):
        # 1. parse
        session_key = request.session.session_key

        # 2. call use case
        output = GetCartUseCase(cart_repo).execute(session_key)

        # 3. present (picks component + builds view model)
        component = CartPresenter().present(output)

        # 4. render whatever comes back — zero decisions
        return component.render_to_response(request=request)

MVP Pattern

Model-View-Presenter. The View is passive — it has no logic, makes no decisions, knows nothing about the model. The Presenter mediates everything between domain output and rendered HTML.

Frontend MVP (view-first)

View is created first, then the presenter is injected into it. The presenter holds a reference back and calls methods on the live view over time. Bidirectional, ongoing binding.

Server-Side MVP (presenter-first)

The presenter is called first and constructs the view. The view renders once and dies. No callbacks, no binding — a single pass. Stateless HTTP collapses the lifecycle.

The naming collision: Django's View class is not the MVP "View". It's the coordinator/controller. The Component is the MVP View — it's the passive renderer. The Django View wires the three MVP actors together.
MVP ActorOur ImplementationResponsibility
ModelDomain entities + CartOutputThe business outcome. What happened.
PresenterCartPresenterTransforms model, picks view, builds view model.
ViewComponent + TemplatePassive renderer. Receives view model, outputs HTML.
(Coordinator)Django View classWires the three actors. Not an MVP actor itself.

The Presenter

The presenter is the bridge between the domain world and the UI world. It is the only class that speaks both languages. It owns three decisions:

Which component?
  • Based on output state
  • Empty → CartEmptyComponent
  • Error → CartErrorComponent
  • Full → CartSummaryComponent
What data shape?
  • Builds the ViewModel
  • Formats Decimal → string
  • Pluralises labels
  • Computes display flags
Returns
  • A configured Component
  • ViewModel injected in
  • Ready to render
  • No further decisions
cart/interfaces/presenters.pypython
class CartPresenter:
    def present(self, output: CartOutput) -> Component:
        if output.is_empty:
            return CartEmptyComponent(
                vm=CartEmptyViewModel(message="Your cart is empty")
            )

        if output.has_error:
            return CartErrorComponent(
                vm=CartErrorViewModel(message=output.error)
            )

        return CartSummaryComponent(
            vm=CartSummaryViewModel(
                items=[
                    CartItemViewModel(
                        product_id=item.product_id,
                        name=item.name,
                        unit_price=f"${item.unit_price:.2f}",
                        quantity=item.quantity,
                        subtotal=f"${item.subtotal:.2f}",
                    )
                    for item in output.items
                ],
                subtotal=f"${output.subtotal:.2f}",
                tax=f"${output.tax:.2f}",
                total=f"${output.total:.2f}",
                item_count=sum(i.quantity for i in output.items),
                item_label=_pluralise(item_count, "item"),
                show_checkout=not output.is_locked,
                show_free_shipping_nudge=output.shipping_delta > 0,
                nudge_message=f"Add ${output.shipping_delta:.2f} for free shipping",
            )
        )

Adding a new cart state (locked during checkout, fraud review, etc.) means adding one component and one branch in the presenter. The view never changes.

View Model

The view model is the typed contract between the presenter and the template. It lives co-located with its component. The template reads vm.* only — it never computes, formats, or makes decisions.

What belongs in the view model

Not business logic — that stays in the domain. View logic is anything that exists purely because of how the UI works:

cart/interfaces/components/cart_summary/cart_summary.pypython
@dataclass
class CartSummaryViewModel:
    # Formatted for display — domain has Decimal, view needs string
    subtotal: str           # "$12.50"
    tax: str               # "$1.87"
    total: str             # "$14.37"

    # Computed display values — derived from domain, meaningless outside UI
    item_count: int
    item_label: str        # "1 item" vs "3 items" — pluralisation is a view concern

    # Display flags — template conditions as named booleans
    show_checkout: bool
    show_free_shipping_nudge: bool

    # UI-specific labels — copy that depends on state
    nudge_message: str     # "Add $5 more for free shipping"
    checkout_label: str    # "Checkout" vs "Continue to Payment"

    items: list[CartItemViewModel]
Domain asks
  • What is true?
  • is_empty
  • shipping_delta (Decimal)
  • is_locked
Presenter answers
  • What should appear?
  • show_nudge
  • nudge_message (str)
  • checkout_label

The template has no questions left to answer. It just reads vm.*.

from dataclasses import dataclass
from django_components import Component, register

@dataclass
class CartItemViewModel:
    product_id: int
    name: str
    unit_price: str
    quantity: int
    subtotal: str

@dataclass
class CartSummaryViewModel:
    items: list[CartItemViewModel]
    subtotal: str
    tax: str
    total: str
    item_count: int
    item_label: str
    show_checkout: bool
    show_free_shipping_nudge: bool
    nudge_message: str

@register("cart-summary")
class CartSummaryComponent(Component):

    def __init__(self, vm: CartSummaryViewModel, **kwargs):
        super().__init__(**kwargs)
        self.vm = vm

    # @property allows dynamic templates based on presentation variants
    @property
    def template(self) -> str:
        return """
        <div class="cart-summary">
          <p>{{ vm.item_label }}</p>

          {% for item in vm.items %}
            <div class="cart-item">
              <span>{{ item.name }}</span>
              <span>{{ item.quantity }} × {{ item.unit_price }}</span>
              <span>{{ item.subtotal }}</span>
            </div>
          {% endfor %}

          {% if vm.show_free_shipping_nudge %}
            <p class="nudge">{{ vm.nudge_message }}</p>
          {% endif %}

          <div class="totals">
            <p>Subtotal: {{ vm.subtotal }}</p>
            <p>Tax: {{ vm.tax }}</p>
            <p><strong>Total: {{ vm.total }}</strong></p>
          </div>

          {% if vm.show_checkout %}
            <a href="{% url 'checkout:start' %}">Checkout</a>
          {% endif %}
        </div>
        """

    css = """
        .cart-summary { padding: 1rem; }
        .cart-item { display: flex; gap: 1rem; padding: .5rem 0; }
        .totals { border-top: 1px solid #eee; margin-top: 1rem; padding-top: 1rem; }
        .nudge { color: var(--green, green); font-size: 13px; }
    """

    def get_context_data(self, **kwargs):
        return {"vm": self.vm}
@property template rule: Use @property for presentation variants (compact vs full layout) — not for state branching. State branching belongs in the presenter. If the property is checking vm.is_empty, move that decision upstream.

Inline Templates

Everything co-located in one file. The view model, component logic, HTML, CSS, and JS live together. Close to how Vue single-file components work.

When to inlineWhen to split to a file
Template under ~20 linesTemplate over ~20 lines
Self-contained, focused componentComplex CSS/JS needing editor support
Internal/private componentDesigners touching the template
Rapid iterationTemplate shared across multiple components

django-components deduplicates CSS and JS automatically — even if a component renders 10 times, the styles load once in <head> and the script once before </body>.

HTMX & Deep Nesting

Deep component nesting is the signal to split the render into separate HTTP calls. Each HTMX endpoint is its own full stack — use case → presenter → component.

The nesting decision tree

QuestionYesNo
Is data already in scope from parent use case?Nest the componentHTMX call
Is this component always visible on load?Nest itHTMX with hx-trigger="revealed"
Is fetching this data expensive?HTMX call, show skeletonNest it
Is this a different domain concern?HTMX call, own presenter chainNest it

class InventoryBadgeView(View):
    def get(self, request, product_id: int):
        output = GetInventoryUseCase(...).execute(product_id)
        component = InventoryPresenter().present(output)
        return component.render_to_response(request=request)

class InventoryPresenter:
    def present(self, output: InventoryOutput) -> Component:
        if output.in_stock:
            return InStockBadgeComponent(vm=InStockViewModel(count=output.count))
        if output.low_stock:
            return LowStockBadgeComponent(vm=LowStockViewModel(count=output.count))
        return OutOfStockBadgeComponent(vm=OutOfStockViewModel())

The page becomes a composition of independent vertical slices. Each slice is independently testable, independently cacheable, and has no knowledge of the others. The browser assembles the page; the server handles clean isolated requests.

vs Laravel Resources

The presenter and a Laravel API Resource are the same concept — they just produce different representations. The presenter's job is take domain output, return the right representation.

Django Presenter → HTML
  • Picks the Component (which template)
  • Builds the ViewModel (formatted data)
  • Conditional via different component class
  • Nested via child components
Laravel Resource → JSON
  • Defines the JSON array shape
  • Formats via number_format, etc.
  • Conditional via when(), mergeWhen()
  • Nested via CartItemResource::collection()
CartResource.php (Laravel)php
class CartResource extends JsonResource
{
    public function toArray($request): array
    {
        return [
            'items'    => CartItemResource::collection($this->items),
            'subtotal' => '$' . number_format($this->subtotal, 2),
            'tax'      => '$' . number_format($this->tax, 2),
            'total'    => '$' . number_format($this->total, 2),
        ];
    }
}

The Laravel controller calling CartResource is identical in role to the Django view calling CartPresenter. Same pattern, different output format.

Industry Standard

Full clean architecture with a presenter layer is not the Django default — but it's a well-reasoned choice for complex domains. Here's where teams actually land:

Rails / Django default
Controller calls service, dict passed to template. Template filters for formatting.
Small/medium teams, moving fast
Cosmic Python
Service layer, repository pattern, domain model. View maps inline. No formal presenter.
Python/Django shops with discipline
What we built
Use case → Presenter → ViewModel → Component. Middle ground with typed view models.
django-components, larger teams
ASP.NET standard
Controller → Presenter → ViewModel → Razor. Typed templates require explicit view models.
C# shops, Razor templates
Strict Uncle Bob
Use case calls presenter via output port interface. Full dependency inversion.
Java/Spring, .NET enterprise
The honest take: The formal presenter class as a distinct layer is more a Java/C# convention. In Python it's a deliberate choice, not a default. The part that has broad consensus is: use cases, repositories, domain entities. The presenter question is answered by most Django teams with template filters. We add it explicitly because django-components creates natural component boundaries that make the presenter-builds-the-component pattern a clean fit.

Summary

The complete responsibility map for every class in the system:

ClassKnows AboutDecides
Domain Entities stdlib only. Business rules, invariants, tax rates. What is true in the domain.
Ports (ABCs) Domain entities only. The interface contract between layers.
Use Case Ports (abstract), domain entities. Business outcome. Returns CartOutput.
Repository (concrete) Port it implements, Django ORM. How to persist and retrieve domain entities.
Presenter Use case output, ViewModels, Component classes. Which component renders. How data is formatted.
ViewModel Nothing (it's a dataclass). Typed contract between presenter and template.
Component Its ViewModel. Its template, CSS, JS. How the HTML is structured.
Template vm.* only. Nothing. Just renders.
Django View Use case, presenter, Django request/response. Nothing. Wires and renders what comes back.
